## 1. Clasificar la plataforma actual

```text
Navegador (ejecuta cliente.html, entregado por Django)
   │
   │ fetch("/entregas/cotizar/?km=..&kg=..") → respuesta JSON
   ▼
nginx :8000 (balanceador)
   ├──► web 1 ─┐
   ├──► web 2 ─┼── misma aplicación Django con gunicorn
   └──► web 3 ─┘   views + recomendador + reglas + medios + modelo .joblib
                │
                ▼
             Postgres
```

- **Cliente:** el navegador, donde se ejecuta la página `cliente.html`.
- **Servidor:** una aplicación Django que corre en tres copias iguales detrás de nginx, con dos procesos de gunicorn por copia.
- **Comunicación con el cliente:** el navegador consulta `/entregas/cotizar/` y recibe los datos en JSON.

**Clasificación:** es un monolito con API.

**Evidencia:** la vista `recomendar`, de `views.py`, utiliza `obtener_recomendador().sugerir(paquete)` mediante un `import` de Python. Eso significa que la vista y el recomendador trabajan dentro del mismo proceso, sin hacer una petición por red entre ellos.

Que existan tres copias de la aplicación no cambia su clasificación. Son réplicas del mismo programa para repartir las peticiones. Sigue siendo un monolito porque cada copia contiene toda la lógica. Tiene API porque el navegador se comunica con Django por HTTP y recibe respuestas en JSON.

## 2. La trampa de los endpoints

Sabemos que es mentira decir que tener `/entregas/hola/`, `/entregas/recomendar/` y una página HTML ya lo convierte en microservicios.

Tener varias rutas solo indica que la aplicación ofrece distintas operaciones. Todas están registradas en `entregas/urls.py` y las atiende el mismo Django. Incluso el archivo `cliente.html` lo entrega esa misma aplicación.

La API permite que el navegador le pida información al servidor, pero eso no significa que las partes del servidor estén separadas en servicios independientes.

Para hablar de microservicios, el recomendador podría ejecutarse como otro servicio, con su propio despliegue, y recibir peticiones del backend por red. Ahí sí habría una separación entre los dos programas.

También habría que decidir qué hacer si ese servicio falla. Por ejemplo, el backend podría usar reglas de respaldo para seguir atendiendo los casos que esas reglas permitan resolver.

## 3. La misma operación en dos mundos

### En el monolito con API

Caso: un paquete sale a las 3:00. El modelo pone al dron como primera opción, pero las reglas lo descartan y termina seleccionándose la moto.

1. El cliente manda un `POST /entregas/recomendar/` y `entregas/urls.py` dirige la petición a la vista `recomendar`.
2. La vista lee el JSON, revisa que estén los campos necesarios y convierte los valores numéricos a `float`. Si los datos no son válidos, devuelve un error 400.
3. Después llama a `obtener_recomendador().sugerir(paquete)`. El modelo se mantiene cargado en memoria una vez por proceso, así que no se vuelve a leer el archivo en cada petición.
4. En `recomendador.py`, el modelo calcula las probabilidades de los medios de entrega y se arma un ranking. En este caso, el dron aparece primero.
5. El recomendador recorre ese ranking y consulta `es_posible`, de `reglas.py`. Como las 3:00 entran en la condición `hora_salida < 6`, el dron se descarta. Luego se revisa la moto y, si cumple las reglas, se devuelve una `Sugerencia` con ese medio y el motivo.
6. La vista usa `crear_medio("moto")`, de `medios.py`, para crear un `EntregaMotocicleta`. Su método `planear(paquete)` calcula los minutos con `distancia_km / 35 * 60` y agrega la indicación de usar una ruta por avenidas.
7. Finalmente, Django responde un JSON con el medio elegido, el motivo y el plan de entrega.

Las llamadas entre la vista, el recomendador, las reglas y los medios se hacen dentro del proceso de Django. Para esa parte del recorrido no se necesita comunicación por red. La petición del navegador al servidor sí viaja por HTTP.

### Si `recomendador` fuera otro servicio

Para el mismo paquete de las 3:00, el recomendador correría aparte, como otro servicio definido en `docker-compose.yml`.

1. La petición llega al backend de Pedidos y la vista valida los datos igual que antes.
2. En lugar de cargar el modelo mediante un `import`, el backend manda los datos por HTTP al servicio de IA, usando una dirección como `http://recomendador:8000/...`.
3. El servicio ejecuta el modelo y devuelve un JSON con el ranking de medios y sus probabilidades.
4. Pedidos revisa ese ranking con `es_posible`. Descarta el dron por la hora y selecciona la moto si cumple las condiciones.
5. El backend calcula el plan con `medios.py` y devuelve la respuesta al cliente.

Ahora hay una llamada por red adicional: la comunicación entre Pedidos y el servicio de IA. Esa llamada puede fallar porque el servicio no esté disponible, haya un problema de conexión o la respuesta tarde demasiado.

Por eso se necesita un tiempo máximo de espera. Si no llega una respuesta válida, Pedidos puede usar `elegir_medio`, de `reglas.py`, como respaldo basado en distancia y peso. El resultado debe aclarar que la selección salió de las reglas y no del modelo. También hay que comprobar que el medio elegido cumpla las restricciones aplicables, incluida la hora de salida.

## 4. Decisión de la empresa

Elegiría la opción B: separar solamente el servicio de IA y mantener el resto como monolito con API.

1. **El modelo ocupa bastante memoria.** El Random Forest pesa alrededor de 50 MB y cada proceso que lo carga mantiene su propia copia. Al moverlo a otro servicio, los procesos de Pedidos ya no necesitan cargarlo. La cantidad de copias del modelo dependerá de cuántos procesos y réplicas tenga el servicio de IA.
2. **El modelo se reentrena cada semana.** Separarlo permite actualizar y desplegar la IA sin reiniciar la parte de Pedidos, siempre que se mantenga compatible la forma de pedir y recibir los datos.
3. **Pedidos cambia poco.** Como esa parte es estable, no hace falta dividirla en más servicios. Hacerlo agregaría llamadas por red, despliegues y posibles fallas sin una necesidad clara en este caso.

La separación también tiene un costo: hay que manejar errores de conexión, respuestas inválidas y tiempos de espera. Aun así, sacar solo la IA tiene sentido porque es la parte pesada y la que se actualiza con más frecuencia.

Si después aparecen otras necesidades, como pagos o una carga distinta de trabajo, se puede volver a revisar la arquitectura.

## 5. Un solo corte

La propuesta es extraer únicamente el servicio de IA.

- **Qué se lleva:** la parte de `recomendador.py` que ejecuta el modelo y los archivos `.joblib`. Recibe los datos del paquete y devuelve el ranking de medios con sus probabilidades.
- **Qué se queda en Pedidos:** `views.py`, `reglas.py` y `medios.py`. El backend valida la petición, aplica las restricciones al ranking, elige el medio y calcula el plan. También conserva `elegir_medio` como respaldo.
- **Qué pasa con el Adapter:** se queda en Pedidos. Su implementación cambia para consultar el servicio por HTTP en lugar de ejecutar el modelo localmente, conservando la interfaz que usa el resto de la aplicación.

**Por qué este corte:** el modelo y sus archivos cambian juntos, así que conviene mantenerlos en el mismo servicio. Las reglas y el cálculo de los medios siguen ligados a las decisiones de Pedidos. Además, el Adapter ya marca un punto donde se puede cambiar la forma de consultar la IA sin repartir ese cambio por toda la aplicación.

**Por qué no un servicio por archivo:** separar `views.py`, `reglas.py` y `medios.py` solo por estar en archivos distintos obligaría a hacer más llamadas por red para resolver una sola petición. Eso agregaría latencia y más puntos de falla. La separación debe responder a una responsabilidad que convenga ejecutar y desplegar aparte, no al número de archivos del proyecto.
